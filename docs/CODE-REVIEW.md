## ۲. رده‌بندی ریسک — عمق بازبینی را همین تعیین می‌کند

هر PR باید در توضیحاتش ردهٔ خودش را اعلام کند.

| رده | دامنه | بازبین لازم | شاهد لازم |
|---|---|---|---|
| **P0 — حیاتی** | مالی/شهریه، معدل و آیین‌نامه، فارغ‌التحصیلی، احراز هویت و نشست، RLS و اسکوپ دانشگاه، مهاجرت دیتابیس، حذف/تغییر داده | ۲ نفر (یکی آشنا به آن دامنه) | اجرای واقعی + خروجی عددی مقایسه‌شده با سیستم قدیم |
| **P1 — مهم** | گزارش‌ها، کوئری‌های تحلیلی، گردش کار، ثبت‌نام، امتحانات | ۱ نفر | اجرای صفحه/گزارش + کد وضعیت |
| **P2 — معمولی** | UI، متن‌ها، مرتب‌سازی، خروجی اکسل، ناوبری | ۱ نفر | اسکرین‌شات |

**PRهای P0 هرگز با «بررسی چشمی» تأیید نمی‌شوند.** اگر نتوانستی اجرا کنی، تأیید نکن — بگو چرا.

## ۳. قوانین سخت (Blocking) — این‌ها همیشه مانع ادغام‌اند

1. **قرمز بودن CI = عدم ادغام.** بدون استثنا. اگر تستی «بی‌ربط» شکسته، اول همان را درست کن.
2. **بدون شاهد اجرا = عدم ادغام.** برای هر تغییر رفتاری: اسکرین‌شات، خروجی کنسول، یا خروجی کوئری در توضیحات PR.
3. **مهاجرت بدون اجرا = عدم ادغام.** `npm run db:migrate` باید روی یک دیتابیس تمیز اجرا شده باشد.
4. **هر Server Action بدون گارد = عدم ادغام.** `node scripts/audit-actions.mjs` باید سبز باشد.
5. **تغییر رفتار مالی/معدل بدون تست واحد = عدم ادغام.**
6. **PR بالای ۴۰۰ خط تغییر مؤثر = بازگردانده می‌شود** (به‌جز مهاجرت‌ها و فایل‌های تولیدی). PR بزرگ، بازبینی سطحی تولید می‌کند.

## ۴. چک‌لیست بازبینی — به ترتیب ریسک

### ۴.۱ داده و SQL (بیشترین منبع باگ در این مخزن)

- [ ] **شناسه‌های camelCase در SQL دابل‌کوت می‌شوند**: `"studentId"` نه `studentId`.
      PostgreSQL شناسهٔ بدون کوت را lowercase می‌کند → `column "studentId" does not exist`.
- [ ] **ستون‌ها واقعاً وجود دارند.** قبل از نوشتن کوئری، `information_schema.columns` را چک کن.
      (`payesh` روی `f.periodId` شکست — ستون وجود ندارد.)
- [ ] **نوع پارامترها صریح cast می‌شوند** وقتی با عدد اعشاری مقایسه می‌شوند:
      `o.capacity * ${threshold}` با `threshold=0.5` → `invalid input syntax for type integer`.
      درست: `o.capacity * ${threshold}::numeric`.
- [ ] **GROUP BY / ORDER BY** فقط عبارت یا نام ستون می‌گیرد، نه alias ضمنی.
      `GROUP BY att.absent  name, code` → `syntax error at or near "name"`.
- [ ] **هر کوئری جدید حداقل یک بار با دادهٔ واقعی اجرا شده**، نه فقط با تایپ‌چک.
- [ ] **حالت خالی پیام توضیحی دارد** («۰ رکورد چون …»)، نه جدول خالی بی‌دلیل.
- [ ] **اسکوپ دانشگاه**: هر کوئری از `getCurrentUniversity()` در **`@/lib/university-scope`** استفاده می‌کند — نه `@/lib/auth`. شرط `universityId = X OR universityId IS NULL` عمدی است؛ حذفش نکن.
- [ ] **اعداد پولی و معدل روی integer** محاسبه می‌شوند، نه float.

### ۴.۲ مهاجرت‌ها

- [ ] فایل جدید در `drizzle/meta/_journal.json` ثبت شده و `count(*)` با `journal.length` می‌خواند (اسکریپت `migrate-db.mjs` در غیر این صورت fail می‌کند).
- [ ] مهاجرت **idempotent** است (`IF NOT EXISTS` / `DO $$ … $$`).
- [ ] روی دیتابیس خالی و روی دیتابیس موجود هر دو اجرا شده.
- [ ] اگر ستونی در `schema.ts` اضافه شده، در SQL هم هست — و برعکس.
- [ ] `npm run db:hardening` بعد از مهاجرت سبز است.

### ۴.۳ امنیت و دسترسی

- [ ] هر Server Action گارد نقش دارد (`requireRole` یا معادلش).
- [ ] ورودی کاربر با `zod` اعتبارسنجی می‌شود.
- [ ] دسترسی به رکورد متعلق به کاربر، **از خود رکورد** استخراج می‌شود، نه از پارامتر ورودی (`auditId` از کلاینت گرفته نشود).
- [ ] policy جدید RLS واقعاً قابل‌ارضا است — `app.user_role` هرگز ست نمی‌شود؛ فقط `app.user_id` و `app.university_id` وجود دارند.
- [ ] هیچ سکرت/توکن/رمز در لاگ یا پیام خطا چاپ نمی‌شود.

### ۴.۴ UI و تجربه

- [ ] صفحه در مرورگر **واقعاً باز و کلیک شده** (نه فقط build موفق).
- [ ] حالت خطا و حالت خالی هر دو دیده شده‌اند.
- [ ] متن‌ها فارسی و راست‌به‌چپ؛ اعداد با `faNum`؛ تاریخ با تقویم جلالی.
- [ ] صفحه‌بندی و خروجی اکسل کار می‌کند (اگر گزارش است).

### ۴.۵ کیفیت کد

- [ ] تابع تکراری ساخته نشده — اول در `src/lib` جست‌وجو کن.
- [ ] خطاها بلعیده نمی‌شوند (`catch {}` خالی ممنوع، مگر با کامنت دلیل).

## ۵. فرآیند

```
۱. خودبازبینی      → diff خودت را قبل از باز کردن PR بخوان
۲. PR + شاهد       → قالب PR را پر کن؛ شاهد اجرا را بگذار
۳. CI              → tsc · test · audit-actions · build · ci-audit · RLS · concurrency
۴. بازبینی انسانی  → طبق ردهٔ ریسک (۱ یا ۲ نفر)
۵. ادغام           → squash، پیام commit به سبک Conventional Commits
۶. راستی‌آزمایی     → برای P0: بعد از استقرار، یک بار روی محیط واقعی چک شود
```

**زمان پاسخ:** بازبینی P0 حداکثر ۴ ساعت کاری، P1/P2 حداکثر ۱ روز کاری. اگر بازبین نمی‌رسد، خودش اعلام کند تا PR معطل نماند.

**مالکیت:** هر تغییر یک بازبین اصلی دارد. تأیید «LGTM» بدون اشاره به حداقل یک نکته یا تأیید صریح چک‌لیست پذیرفته نیست.

## پیوست ب — شاهد اجرا برای گزارش‌ها

برای هر گزارش جدید، سه چیز لازم است:

1. **کد وضعیت** — گزارش با `ADMIN` باز می‌شود.
2. **تعداد ردیف** — عدد واقعی، نه «کار می‌کند».
3. **حالت خالی** — چرا صفر رکورد؟ (اگر دلیلش مشخص نیست، باگ است.)

نمونهٔ شکست واقعی که این قاعده می‌گرفت:

| گزارش | خطای واقعی سرور |
|---|---|
| `payesh` | `column f.periodId does not exist` |
| `low-enrollment` | `invalid input syntax for type integer: "0.5"` |
| `attendance-list` | `syntax error at or near "name"` |

هر سه با یک بار کلیک «اجرای گزارش» پیدا می‌شدند — و هیچ‌کدام در `tsc` یا `build` دیده نمی‌شوند.
