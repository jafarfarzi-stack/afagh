# Runbook پاسخ به حادثهٔ امنیتی (Incident Response Runbook)

> **نسخهٔ سند:** 1.0 — **تاریخ:** 2026-10-19  
> **دامنهٔ اعمال:** استقرارهای پروداکشن سامانهٔ آفاق  
> **مکمل:** `SECURITY-POLICY.md` · `DEPLOY-SECURITY-CHECKLIST.md` · `SECRETS-ROTATION-PROCEDURE.md`

این Runbook، گام‌های عملیاتی پاسخ به حادثهٔ امنیتی را برای تیم استقرار/عملیات تعریف می‌کند. هدف: **کاهش خسارت، بازیابی سریع، و یادگیری**.  
در هر حادثه، ابتدا **امنیت دادهٔ دانشجویان** و **پایداری سرویس** در اولویت است.

---

## ۱) نقش‌ها (Roles)

| نقش | مسئولیت |
|---|---|
| **فرماندهٔ حادثه (IC)** | هماهنگی کل، تصمیم‌گیری، ارتباط با ذی‌نفعان |
| **عملیات فنی (Ops)** | اجرای دستورها روی سرور، تغییر پیکربندی، بازیابی |
| **امنیت (Sec)** | تحلیل، جمع‌آوری شواهد، تعیین دامنهٔ نفوذ |
| **ارتباطات (Comms)** | اطلاع‌رسانی به دانشگاه/کاربران (در صورت نیاز) |
| **پشتیبان داده (DBA)** | پشتیبان/بازیابی/بررسی RLS و یکپارچگی |

در تیم‌های کوچک، یک نفر می‌تواند چند نقش را برعهده بگیرد، اما **فرماندهٔ حادثه** باید یک نفر واحد باشد.

---

## ۲) سطوح شدت (Severity)

| سطح | تعریف | مثال |
|---|---|---|
| **S1 — بحرانی** | نشت دادهٔ شخصی/مالی، کنترل سرور، RLS شکسته | SQL injection موفق، رمز owner لو رفته، دسترسی غیرمجاز به کارنامهٔ همهٔ دانشجویان |
| **S2 — بالا** | دور زدن احراز هویت/مجوز، نشت سکرت، قطع سرویس | CSRF روی عملیات مالی، XSS ذخیره‌شده، قفل‌شدن حساب‌ها |
| **S3 — متوسط** | نشت محدود، bypass جزئی، degraded security | rate limit bypass، افشای متادیتای غیرحساس |
| **S4 — پایین** | یافتهٔ اطلاعاتی، hardening | هدر اضافی، پیکربندی غیربهینه |

**زمان پاسخ هدف:** S1: ۱ ساعت · S2: ۴ ساعت · S3: ۱ روز · S4: نسخهٔ بعدی.

---

## ۳) تشخیص (Detection)

منابع تشخیص:

- لاگ‌های ساختاریافتهٔ اپ (`docker compose logs -f app`)
- لاگ scheduler (`[CRITICAL]`, `[ALERT]`, `[scheduler]`)
- هشدارهای `make health`
- گزارش کاربران / پژوهشگران امنیتی
- پایش بیرونی (SIEM/Loki/ELK) اگر پیکربندی شده
- anomalous DB queries / تغییرات ناگهانی در داده

**نشانه‌های مهم:**

- درخواست‌های mutating بدون `Origin`/`Referer` با کوکی (هشدار `[csrf]`)
- خطاهای `requireStudentScope` / `canActOnUniversity` (تلاش دسترسی cross-tenant)
- خطای `assertProdSecrets` یا `check-env` در startup
- ورودهای ناموفق مکرر / قفل حساب
- تغییرات غیرمنتظره در جداول مالی/نمرات

## ۴) گام‌های پاسخ (Timeline)

### ۴.۰) اولین ۱۵ دقیقه (Triage)

1. **فرماندهٔ حادثه** را مشخص کنید.  
2. شدت (S1–S4) را تعیین و ثبت کنید.  
3. دامنهٔ اثر را تخمین بزنید: کدام سرویس، کدام داده، کدام کاربران.  
4. کانال ارتباطی داخلی بسازید (گروه/کانال) و رویدادها را ثبت کنید.  
5. **شواهد را حفظ کنید** (لاگ‌ها، snapshot) قبل از هر تغییر.

```bash
# وضعیت سرویس‌ها
make ps

# لاگ زندهٔ اپ (۲۰۰ خط آخر)
docker compose logs --tail=200 app

# لاگ همهٔ سرویس‌ها
docker compose logs --tail=200
```

### ۴.۱) مهار (Containment) — توقف گسترش

**اگر S1/S2:**

- **قطع دسترسی عمومی** (در صورت نیاز):  
  ```bash
  # bind فقط به loopback (پیش‌فرض) — اگر 0.0.0.0 شده بود، برگردانید
  # در .env: APP_BIND=127.0.0.1
  make down
  ```
- **مسدودسازی IP مهاجم** در فایروال/پروکسی (Caddy/Nginx/ufw).  
- **غیرفعال‌سازی حساب‌های دمو** (اگر فعال بودند):  
  ```bash
  # در .env
  AFAGH_DEMO_MODE=0
  # rebuild + up
  make rebuild
  ```
- **مسدودسازی endpointهای cron** (در صورت نشت کلید): حذف/چرخش `x-cron-secret`ها (نگاه کنید به `SECRETS-ROTATION-PROCEDURE.md`).  
- **غیرفعال‌سازی scheduler** (در صورت نیاز):  
  ```bash
  docker compose stop scheduler
  ```

**مهار نرم (بدون قطع سرویس):**

- چرخش سکرت‌های لو رفته (DB/Redis/MinIO/OTP pepper/…) — بخش ۵.
- ابطال نشست‌ها: تغییر `TICKET_TOKEN_SECRET` (و `PREVIOUS_TICKET_TOKEN_SECRET` برای گذار) یا رمز کاربران.
- مسدودسازی کاربر/نقش مهاجم در پایگاه‌داده (در صورت شناسایی).

### ۴.۲) ریشه‌یابی و پاک‌سازی (Eradication)

1. **حذف دسترسی مهاجم:** حذف کاربر/نقش/توکن، تغییر رمزها.  
2. **پاک‌سازی کد/دادهٔ مخرب:**  
   - بررسی تغییرات غیرمجاز در DB (audit trail، جداول مالی/نمرات).  
   - بررسی فایل‌های آپلودشدهٔ مشکوک در volume `afagh_uploads`.  
   - بررسی اسکریپت‌های اضافه در کانتینر (نباید باشد؛ ایمیج immutable است).  
3. **اعمال پچ:** اصلاح کد/پیکربندی، build مجدد، deploy.  
4. **اجرای hardening:**  
   ```bash
   make migrate   # یا docker compose run --rm migrator
   ```
5. **بررسی RLS:**  
   ```bash
   make drill     # بازگردانی + مقایسه + RLS
   ```

### ۴.۳) بازیابی (Recovery)

1. **پشتیبان‌گیری از وضعیت فعلی** (حتی اگر آلوده است — برای تحلیل):  
   ```bash
   make backup
   make copy-backups-to-host DEST=/tmp/incident-$(date +%F)
   ```
2. **بازگردانی از آخرین پشتیبان سالم** (در صورت نیاز):  
   ```bash
   make verify-backup
   make restore-dump FILE=backups/afagh-….dump
   make drill
   ```
3. **راه‌اندازی سرویس:**  
   ```bash
   make up
   make health
   ```
4. **تأیید:** ورود، RLS، عملیات حساس (مالی/نمرات)، cron.  
5. **پایش افزایش‌یافته** برای ۲۴–۷۲ ساعت.

### ۴.۴) پس از حادثه (Post-Incident)

- **گزارش پس از حادثه (PIR)** ظرف ۵ روز کاری:  
  - جدول زمانی (timeline)  
  - علت ریشه‌ای (root cause)  
  - اثر (دادهٔ لو رفته، کاربران، مدت)  
  - اقدامات انجام‌شده  
  - اقدامات پیشگیرانه (action items) با مالک و مهلت  
- **اطلاع‌رسانی** به دانشگاه/کاربران در صورت نشت دادهٔ شخصی (طبق مقررات).  
- **به‌روزرسانی** Runbook/Checklist/Policy در صورت یافتن شکاف.  
- **ثبت** در دفتر حادثه و دفتر چرخش سکرت.

## ۵) پاسخ‌های ویژه (Specialized Playbooks)

### ۵.۱) نشت سکرت (Secret Leak)

1. **شناسایی** کدام سکرت لو رفته (DB owner/app, Redis, MinIO, cron, SAMIN, OTP pepper, ticket token, backup signing).  
2. **چرخش فوری** طبق `SECRETS-ROTATION-PROCEDURE.md` (بخش مربوطه).  
3. **ابطال نشست‌ها** (تغییر `TICKET_TOKEN_SECRET` + `PREVIOUS_TICKET_TOKEN_SECRET`).  
4. **بررسی لاگ‌ها** برای استفادهٔ غیرمجاز از سکرت (IP/زمان).  
5. **در صورت نشت DB owner password:** فرض کنید کل DB در خطر است → بازیابی از پشتیبان پیش از نشت + چرخش همهٔ سکرت‌ها.  
6. **ثبت** در دفتر چرخش سکرت.

### ۵.۲) نشت دادهٔ شخصی (PII Breach)

1. **مهار:** قطع دسترسی عمومی در صورت نیاز.  
2. **تعیین دامنه:** کدام جداول/ردیف‌ها، چند نفر، چه نوع داده (ملی، مالی، نمرات).  
3. **شواهد:** snapshot از DB و لاگ‌ها.  
4. **اطلاع‌رسانی:** به مسئول حفاظت از دادهٔ دانشگاه، و در صورت لزوم به افراد.  
5. **رفع ریشه:** اصلاح کنترل دسترسی/RLS/CSRF.  
6. **ثبت** در دفتر حادثه + گزارش به مراجع در صورت الزام قانونی.

### ۵.۳) شکست RLS / دسترسی cross-tenant

1. **قطع فوری** اپ (fail-closed بهتر از نشت).  
2. **بررسی** `hardening.mjs` و نقش `afagh_app` (آیا `BYPASSRLS` دارد؟).  
3. **اجرای مجدد hardening:** `make migrate` (migrator hardening را اجرا می‌کند).  
4. **drill** و تست دستی دسترسی بین دانشگاه‌ها.  
5. **بررسی لاگ** برای درخواست‌های غیرمجاز انجام‌شده.  
6. **اطلاع‌رسانی** در صورت نشت.

### ۵.۴) باج‌افزار / تخریب داده (Ransomware / Data Destruction)

1. **قطع فوری** همهٔ سرویس‌ها و دسترسی شبکه.  
2. **قطع اینترنت** سرور (در صورت امکان).  
3. **بازیابی** از پشتیبان آفلاین (NAS/مقصد بیرونی) — نه از volume محلی (ممکن است آلوده باشد).  
4. **بررسی یکپارچگی** پشتیبان (`verify-backup`, `drill`).  
5. **ساخت محیط جدید** روی سرور تمیز (نه بازیابی روی همان سرور).  
6. **چرخش همهٔ سکرت‌ها** (فرض کنید همه لو رفته‌اند).  
7. **بررسی** ورود/RLS/مالی.

### ۵.۵) قطع سرویس / DoS

1. **تشخیص** لایه (شبکه، اپ، DB، Redis).  
2. **پایش** `make ps`, `docker stats`, لاگ‌ها.  
3. **محدودسازی** در پروکسی (rate limit، IP block).  
4. **افزایش منابع** در صورت نیاز (swap, RAM).  
5. **بررسی** scheduler و cron برای بار اضافی.  
6. **پس از پایداری:** تحلیل علت، بهبود capacity.

## ۶) جمع‌آوری شواهد (Evidence Collection)

```bash
# snapshot لاگ‌ها
docker compose logs --no-color > /tmp/incident-logs-$(date +%F-%H%M).txt

# وضعیت کانتینرها
docker compose ps > /tmp/incident-ps-$(date +%F-%H%M).txt

# snapshot پایگاه‌داده (فقط در صورت نیاز و با احتیاط)
make backup
make copy-backups-to-host DEST=/tmp/incident-db-$(date +%F)

# hash فایل‌های کلیدی
sha256sum .env docker-compose.yml deploy/scheduler.sh > /tmp/incident-hashes.txt
```

**احتیاط:** هرگز `.env` یا سکرت‌ها را در کانال عمومی/issue ارسال نکنید. شواهد را در مسیر امن (encrypted storage) نگه دارید.

---

## ۷) ارتباطات (Communications)

- **داخلی:** فوری (گروه/کانال عملیات).  
- **دانشگاه/ذی‌نفعان:** در صورت S1/S2 یا نشت داده، ظرف ۲۴ ساعت اطلاع‌رسانی اولیه.  
- **کاربران:** پیام در پنل/ایمیل در صورت تأثیر بر سرویس یا داده.  
- **افشای عمومی:** فقط پس از رفع و با هماهنگی؛ از افشای جزئیات بهره‌برداری پرهیز کنید.

---

## ۸) کارهای «انجام ندهید» (Don'ts)

- ❌ قبل از حفظ شواهد، سرور را rebuild/down نکنید.  
- ❌ سکرت‌های لو رفته را فقط «پنهان» کنید؛ باید چرخش شوند.  
- ❌ پشتیبان آلوده را روی همان سرور بازیابی نکنید.  
- ❌ حادثه را در issue عمومی یا commit message فاش نکنید.  
- ❌ بدون فرماندهٔ حادثه، تصمیم‌های بزرگ (قطع سرویس، اطلاع‌رسانی عمومی) نگیرید.  
- ❌ `ALLOW_WEAK_SECRETS=1` را در production روشن نکنید.
