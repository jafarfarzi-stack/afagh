# سیاست امنیتی سامانه آفاق (Security Policy)

> **نسخهٔ سند:** 1.0 — **تاریخ:** 2026-10-19  
> **دامنهٔ اعمال:** کد، استقرار و عملیات سامانهٔ جامع آفاق (Afagh ERP)  
> **شاخهٔ مرجع:** `security/phase2` (RC-1 → RC-2)

این سند، سیاست امنیتی رسمی پروژهٔ آفاق است: چه نسخه‌هایی پشتیبانی می‌شوند، چگونه یک آسیب‌پذیری را به‌صورت مسئولانه گزارش کنید، و تیم چگونه به آن پاسخ می‌دهد.  
برای جزئیات عملیاتی به [`INCIDENT-RESPONSE-RUNBOOK.md`](./INCIDENT-RESPONSE-RUNBOOK.md)، [`DEPLOY-SECURITY-CHECKLIST.md`](./DEPLOY-SECURITY-CHECKLIST.md) و [`SECRETS-ROTATION-PROCEDURE.md`](./SECRETS-ROTATION-PROCEDURE.md) مراجعه کنید.

---

## ۱) نسخه‌های پشتیبانی‌شده (Supported Versions)

| نسخه / شاخه | وضعیت پشتیبانی | دریافت اصلاح امنیتی |
|---|---|---|
| `security/phase2` (RC-1 / RC-2 در حال آماده‌سازی) | ✅ پشتیبانی فعال | بله — اصلاحات امنیتی روی همین شاخه اعمال می‌شوند |
| `FINAL` (شاخهٔ قدیمی) | ⚠️ فقط تاریخی | خیر — برای پروداکشن استفاده نکنید |
| نسخه‌های قدیمی‌تر / تگ‌های پیش از RC-1 | ❌ بدون پشتیبانی | خیر |
| شاخه‌های توسعهٔ شخصی / فورک‌ها | ❌ خارج از محدوده | بستگی به نگهدارندهٔ فورک دارد |

**سیاست نسخه:**

- فقط **آخرین نسخهٔ candidate** (در حال حاضر RC-1/RC-2 روی شاخهٔ `security/phase2`) اصلاح امنیتی دریافت می‌کند.
- پس از انتشار `v1.0.0`، فقط **آخرین minor** و **پچ قبلی** (N و N-1) برای مدت محدود (۶ ماه) پشتیبانی امنیتی خواهند داشت.
- اصلاحات امنیتی به‌صورت **backport به شاخهٔ پشتیبانی‌شدهٔ فعلی** اعمال می‌شوند؛ به شاخه‌های قدیمی backport نمی‌شود.
- تغییرات breaking در سیاست امنیتی (مثلاً اجباری‌شدن یک متغیر ENV) در `RELEASE-READINESS.md` و چک‌لیست استقرار مستند می‌شوند.

## ۲) تماس و افشای مسئولانه (Responsible Disclosure)

### ۲.۱) چگونه گزارش دهید

اگر یک آسیب‌پذیری امنیتی یافتید، **به‌صورت خصوصی** گزارش دهید و پیش از افشای عمومی، به تیم فرصت رفع بدهید.

- **کانال اصلی:** ایمیل تیم امنیت / مسئول استقرار (مقدار `AFAGH_SUPPORT_EMAIL` در `.env` یا پنل مدیر ← «پیکربندی سامانه»).
- **الگوی آدرس (پیشنهادی):** `security@<دامنهٔ دانشگاه>` (مثلاً `security@afagh.ac.ir`) — این آدرس باید در استقرار واقعی تنظیم و پایش شود.
- **موضوع ایمیل:** `[SECURITY] <عنوان کوتاه>`  
- **پیوست‌ها:** PoC حداقلی، لاگ‌ها (بدون دادهٔ واقعی دانشجویان)، نسخهٔ سامانه (`git describe` / `/api/health`).

> ⚠ **هرگز** آسیب‌پذیری را در issue عمومی، کانال‌های پیام‌رسان، یا commit message فاش نکنید.  
> ⚠ از **دادهٔ واقعی دانشجویان** در PoC استفاده نکنید؛ دادهٔ آزمایشی یا ردیف‌های ساختگی بسازید.

### ۲.۲) محتوای گزارش (حداقل)

1. شرح آسیب‌پذیری و اثر (impact)  
2. مسیر/endpoint/ماژول متأثر  
3. مراحل بازتولید (reproduction steps)  
4. پیش‌شرط‌ها (نقش کاربر، دسترسی، تنظیمات)  
5. نسخهٔ سامانه و commit hash  
6. پیشنهاد رفع (اختیاری اما مفید)  
7. آیا در حال بهره‌برداری است؟ (active exploitation)

### ۲.۳) جدول زمانی (SLA)

| مرحله | زمان هدف |
|---|---|
| تأیید دریافت گزارش | ۵ روز کاری |
| تریاژ و تعیین شدت | ۱۰ روز کاری |
| اصلاح بحرانی (Critical) | ۱۵ روز کاری |
| اصلاح بالا (High) | ۳۰ روز کاری |
| اصلاح متوسط/پایین | نسخهٔ بعدی / برنامهٔ عادی |
| افشای هماهنگ (coordinated disclosure) | پس از انتشار اصلاح، با توافق |

### ۲.۴) قلمرو (Scope)

**در محدوده (in scope):**

- اپلیکیشن وب Next.js و Route Handlerها / Server Actionها
- APIهای داخلی (`/api/*`) و cron endpointها
- پایگاه‌دادهٔ PostgreSQL و سیاست RLS
- Object Storage (MinIO/S3) و بایگانی مدارک
- اسکریپت‌های استقرار/مهاجرت/پشتیبان (`deploy/`, `scripts/`)
- احراز هویت، نشست، CSRF، محدودهٔ دانشگاه/گروه (tenant/object scope)

**خارج از محدوده (out of scope):**

- حملات مهندسی اجتماعی علیه کارکنان
- حملات DoS/DDoS حجمی علیه زیرساخت (گزارش دهید اما در این سیاست پوشش داده نمی‌شود)
- آسیب‌پذیری‌های نرم‌افزارهای ثالث که پچ upstream دارند (گزارش به upstream)
- یافته‌های «اطلاعاتی» بدون اثر امنیتی واقعی (مثلاً نسخهٔ سرور در هدر)
- حساب‌های دمو که عمداً در محیط نمایشی فعال شده‌اند (اگر `AFAGH_DEMO_MODE=1` و `AFAGH_ALLOW_INSECURE_DEMO=true` باشد، رفتار مورد انتظار است، نه آسیب‌پذیری)

### ۲.۵) پناهگاه امن (Safe Harbor)

پژوهشگرانی که با حسن نیت و در چارچوب این سیاست عمل کنند، تحت پیگرد قانونی قرار نمی‌گیرند، به شرطی که:

- فقط به دادهٔ خود یا دادهٔ آزمایشی دسترسی یابند؛
- از آسیب‌پذیری برای دسترسی/تغییر/حذف دادهٔ دیگران استفاده نکنند؛
- حداقل دادهٔ لازم برای اثبات را جمع‌آوری کنند و آن را پس از رفع حذف کنند؛
- افشای عمومی را تا انتشار اصلاح به تأخیر بیندازند.

## ۳) خلاصهٔ کنترل‌های امنیتی پیاده‌سازی‌شده

| حوزه | کنترل |
|---|---|
| احراز هویت / نشست | کوکی نشست با `SameSite` خودکار (HTTPS → None+Secure)، سقف نشست قابل تنظیم (`AFAGH_SESSION_MAX_HOURS`، پیش‌فرض ۴ ساعت)، `mustChangePassword` برای مدیر اولیه |
| CSRF | `assertSameOrigin` / `assertCsrf` برای Route Handlerها؛ `assertServerActionOrigin` برای Server Actionهای حساس (fail-closed) |
| مجوز سطح-شیء | `requireStudentScope` / `requireStudentUniversity` — پیش‌فرض `department`، مرز دانشگاه همیشه fail-closed |
| RLS | نقش محدود `afagh_app` بدون `BYPASSRLS`؛ `withUserRls`؛ RLS fail-closed در production (بدون escape hatch) |
| سکرت‌ها | سیاست واحد در `scripts/lib/secret-policy.mjs`؛ گیت `make check-env`؛ `assertProdSecrets` در startup؛ حداقل ۲۴ کاراکتر برای DB/Redis |
| Object Storage | `checkObjectStoreCredentials`؛ رد پیش‌فرض‌های توسعه (`afagh` / `afagh-secret`) |
| پشتیبان | `pg_dump -Fc` + `sha256` + `LATEST` در volume ماندگار؛ `verify-backup`؛ `drill` |
| مهاجرت | مهاجرت نسخه‌دار (`drizzle/*.sql` + دفتر مهاجرت)؛ پشتیبان پیش از مهاجرت؛ baseline خودکار برای نصب‌های قدیمی |
| حساب اولیه | رمز تصادفی، `mustChangePassword=1`، نوشتن در `bootstrap-credential.txt` (۰۶۰۰)، بدون چاپ در ترمینال |
| حالت دمو | `AFAGH_DEMO_MODE=0` در production؛ قفل دمو در ایمیج تولید (`AFAGH_DEMO_LOCK=1`) |
| شبکه | `dbnet` داخلی (بدون اینترنت)؛ سرویس‌ها فقط روی `127.0.0.1`؛ `no-new-privileges`؛ `cap_drop: ALL` |
| لاگ/ردیابی | لاگ ساختاریافتهٔ JSON؛ هشدار CSRF no-origin؛ لاگ `[ALERT]` در scheduler |

## ۴) گزارش‌دهی داخلی و ثبت

- هر حادثهٔ امنیتی باید در دفتر حادثه (Incident Log) ثبت شود (تاریخ، شدت، مسئول، وضعیت، اقدامات).
- اصلاحات امنیتی باید با پیام commit شفاف (`fix(security): …`) و ارجاع به issue/گزارش مستند شوند.
- تغییر سکرت‌ها باید در دفتر چرخش سکرت ثبت شود (نگاه کنید به `SECRETS-ROTATION-PROCEDURE.md`).

---

## ۵) سلب مسئولیت

این سند «بهترین تلاش» (best-effort) است و تضمین امنیت مطلق نمی‌دهد. امنیت نهایی به پیکربندی صحیح استقرار، پایش مستمر و رعایت چک‌لیست استقرار بستگی دارد.  
برای موارد بحرانی، بلافاصله از Runbook پاسخ به حادثه پیروی کنید.
