# سامانه جامع آموزشی دانشگاه آفاق — فاز صفر (هسته قابل اجرا)

پیاده‌سازی اجرایی طرح «سامانه جامع آموزشی» (سند طراحی: `uploads/geminiafagh.md`).

> **اصل بنیادین طرح:** هیچ قانون آموزشی/اداری در کد هاردکد نشده است؛ همهٔ قوانین
> از جداول داده خوانده می‌شوند: `educational_regulations.rulesConfig`،
> `process_definitions/steps/transitions`، `course_rules.logicTree`،
> `notification_templates`، `student_id_formulas` و `term_financial_rules`.
> تغییر قوانین = تغییر داده، نه استقرار مجدد.

---

## نصب و اجرا

```bash
cd afagh-erp
npm install          # فقط better-sqlite3
npm run reset        # ساخت دیتابیس + کاشت داده سناریومحور (پاکسازی کامل)
npm start            # http://localhost:3000
```

- دیتابیس: `data/afagh.db` (SQLite، WAL، foreign keys فعال)
- سرور پس از `npm run reset` نیازی به ری‌استارت ندارد (اتصال به‌طور خودکار به فایل جدید بازمی‌گردد).
- اسکریپت‌ها: `start` ← `src/server.js` | `seed` ← `src/db/seed.js` | `reset` ← seed با `--reset`

## سناریوهای آماده دمو (همه در صفحه ورود کلیک‌پذیرند)

1. **گیت مالی زینب** — هر سبدی → خطای سخت «پرداخت علی‌الحساب الزامی است».
2. **سقف ۱۴ رضا** — سبد ۱۷ واحدی → خطای سخت «سقف واحد شما ۱۴ است» (منبع: آیین‌نامه مشروطی).
3. **سقف ۲۴ مریم** — معدل ≥ ۱۷ به‌طور خودکار سقف را به ۲۴ می‌برد.
4. **ترم آخر سینا** — تشخیص خودکار باقیمانده ≤ ۸ واحد.
5. **تداخل امتحانی** — «ساختمان داده» گروه ۱ و «برنامه‌نویسی پیشرفته» هر دو امتحان 2026-12-25 ساعت 10:00 دارند؛ اخذ هر دو → خطای نرم → با تیک «ارجاع به شورا» → پرونده PREREQ_WAIVER با کد رهگیری AF-XXXXXX → کارتابل مدیر گروه → معاون → ثبت قطعی + صدور خودکار هزینه.
6. **حسن (آیین‌نامه ۱۳۹۰)** — ریاضی ۱ رد (7.75) سپس قبول (14): هر دو نمره در معدل می‌مانند (KEEP_ALWAYS) در برابر سیاست ۱۴۰۳ (EXCLUDE_IF_PASSED).
7. **درخت پیش‌نیاز** — math2←math1، prog2←prog1، data←(prog1 AND math1 با حد قبولی ویژه ۱۲ در چارت ۱۴۰۳)، arch←(prog2 OR logic)، db←data، net←arch.
8. **SLA** — هر مرحله مهلت دارد (مدیر گروه ۱۲h AUTO_REJECT، معاون 24h ESCALATE)؛ زمان‌بند هر ۶۰ ثانیه `runSlaSweeper` را اجرا می‌کند و مدیر می‌تواند دستی هم اجرا کند (دکمه در صفحه KPI).
9. **Silent Billing** — ثبت واحد بدهی متغیر در `student_ledger` می‌نویسد اما انتخاب واحد را مسدود نمی‌کند؛ گلوگاه‌های تسویه در ماژول مالی فاز بعد.

## معماری (فاز صفر)

```
src/
├─ server.js            # HTTP خالص Node + REST API + زمان‌بند SLA
├─ db/
│  ├─ index.js          # اتصال SQLite + Proxy خودکار به فایل تازه پس از reset + scrypt
│  ├─ schema.sql        # اسکیمای کامل ۱۲ لایه + v_student_balance
│  └─ seed.js           # داده سناریومحور (قوانین، دروس، دانشجویان، BPM، مالی)
├─ engines/
│  ├─ regulations.js    # موتور آیین‌نامه‌ها (سقف واحد، مشروطی، ترم آخر، رویداد پایان ترم)
│  ├─ gpa.js            # کارنامه/معدل با سیاست نمره ردی + دروس توصیفی
│  ├─ enrollment.js     # خط لوله ۵ فیلتری انتخاب واحد + waitlist + شورا + Silent Billing
│  ├─ workflow.js       # BPM داده‌محور، SLA، KPI، گلوگاه‌ها
│  └─ rbac.js           # دسترسی داده‌محور + Audit با زنجیره sha256
└─ public/index.html    # پنل وب فارسی RTL (تک‌فایل، بدون CDN)
```

- **خط لوله انتخاب واحد:** ① گیت مالی (سخت) ← ② وضعیت/بازه/تکرار درس (سخت) ← ③ سقف واحد (سخت، در سطح سبد) ← ④ درخت پیش‌نیاز AND/OR (نرم) ← ⑤ تداخل کلاس/امتحان (نرم).
- **خطاهای نرم** با «ارجاع به شورا» به گردش کار تبدیل می‌شوند (PENDING_COUNCIL) و پس از تایید نهایی، ثبت + صدور وجه به‌صورت تراکنشی انجام می‌شود.
- **waitlist** رتبه‌ای است؛ حذف درس → بازپرداخت CREDIT → ارتقای خودکار نفر بعد + اعلان از `notification_templates`.

## تست بار (۲۰۰۰ کاربر همزمان در انتخاب واحد)

```bash
npm run stress -- seed 2000   # ساخت ۲۰۰۰ دانشجوی آزمایشی (idempotent)
npm run stress -- run 2000 250   # ورود+لیست دروس+ثبت سبد با همزمانی ۲۵۰
npm run stress -- data 2000      # آذرخش: ۲۰۰۰ درخواست همزمان روی مسیر داده
npm run reset                    # پاکسازی و بازگشت به دموی تمیز
```

نتایج روی **۲ هسته CPU** (سخت‌افزار حداقلی؛ پروداکشن چند برابر سریع‌تر):

| مسیر | p50 | p95 | توضیح |
|---|---|---|---|
| ثبت سبد (همزمانی ۲۵۰) | ۳ms | ۳۴ms | ✅ صفر خطا در ۲۰۰۰/۲۰۰۰ |
| لیست دروس (همزمانی ۲۵۰) | ۲ms | ۲۹ms | سنگین‌ترین خواندن |
| آذرخش ۲۰۰۰تایی همزمان | توان ۲۸۹/ثانیه | — | ✅ صفر خطا؛ حافظه ۲۵۵MB؛ DB ۵.۷MB |
| ورود | ~۵.۵s در ازدحام کامل | — | گلوگاه عمدی: scrypt روی CPU (توضیح ↓) |

**تحلیل ورود:** تأیید رمز scrypt عمداً CPU-بر است (~۴۳ms؛ روی ۲ هسته یعنی ~۴۶ ورود/ثانیه). این یک ویژگی امنیتی ضد بروت‌فورس است، نه ضعف سامانه — با تعداد هسته‌ها خطی مقیاس می‌شود (۸ هسته ≈ ۱۸۵/ثانیه، ۳۲ هسته ≈ ۷۴۰/ثانیه). برای لحظه افتتاح بازه انتخاب واحد، طرح اصلی همان‌جاست که پاسخ می‌دهد: **اتاق انتظار مجازی + صف Redis** (فاز بعد). هزینه scrypt با متغیر محیطی `AFAGH_SCRYPT_N` قابل تنظیم است.

### بهینه‌سازی‌های اعمال‌شده برای بار بالا
- تأیید رمز async روی threadpool لایب‌یو (`UV_THREADPOOL_SIZE=8`) — بلاک‌نکردن event-loop
- ۱۵ ایندکس روی جدول‌های داغ (enrollments، schedules، financial_clearances، …)
- `busy_timeout=5000` + `synchronous=NORMAL` + صفحه‌کش ۳۲MB (WAL)
- تشخیص جایگزینی فایل DB حداکثر هر ۵۰۰ms (نه هر کوئری)

## ماژول ۵ — ثبت نمرات، OTP، اعتراض و بستن ترم ✅ (پیاده‌سازی شد)

چرخه حیات نمره مطابق سند: `PENDING → DRAFT → TEMPORARY → APPEALED → FINALIZED`

| قابلیت | توضیح |
|---|---|
| **گیت ارزشیابی** | دانشجو تا فرم ارزشیابی گمنام را پر نکند نمره‌اش را نمی‌بیند؛ پاسخ‌ها بدون هیچ ارجاع به دانشجو ذخیره می‌شوند (فرم‌ساز پویا: سوال/گزینه/وزن = داده) |
| **ثبت موقت** | نمره برای دانشجو ظاهر و دکمه اعتراض فعال می‌شود (بازه قانونی از `academic_terms.appealWindowDays`) |
| **اعتراض (BPM)** | مستقیم به کارتابل استاد؛ مهلت پاسخ `professorAppealSlaDays`؛ تایم‌اوت → قطعی خودکار + گزارش به مدیر گروه |
| **OTP نهایی‌سازی** | کد ۵ رقمی، اعتبار ۲ دقیقه، حداکثر ۳ تلاش؛ تلاش سوم = قفل + هشدار امنیتی به مدیریت (سطح بانکی) |
| **امضای دیجیتال** | هش SHA-256 کل لیست نمرات فریز می‌شود؛ `تطبیق امضای نمرات` در پنل مدیر دستکاری مستقیم DB را فوراً کشف می‌کند |
| **بستن ترم خودکار** | با قطعی‌شدن آخرین درسِ دانشجو: اسنپ‌شات کارنامه + ارزیابی `evaluateEndOfTerm` (مشروطی/اتمام سنوات → `BLOCKED_COMMISSION` + کمیسیون) |
| **ددلاین هوشمند** | SLA موتور: ۷۲h و ۲۴h مانده پیام یادآوری به استاد؛ گذشت مهلت → ارجاع به مدیر گروه |

حساب‌های دمو جدید: استاد رضایی `0011111111` (ریاضی۲/پروگرم۲/شبکه) و استاد احمدی `0022222222` (داده/اندیشه/پایان‌نامه) — مسیر تست: کلاس‌های من ← ورود نمرات ← ثبت موقت ← (دانشجو: ارزشیابی ← مشاهده نمره ← اعتراض) ← ارسال کد و نهایی‌سازی.

## ماژول ۶ — مدیریت امتحانات، تخصیص صندلی و مراقبین ✅ (پیاده‌سازی شد)

موتور سه‌فازی چیدمان ضدتقلب (سند §۱۵۰۰) در `src/engines/exams.js`:

| فاز | عمل |
|---|---|
| ۱ — گروه‌بندی ساختاریافته | بلوک‌بندی بر اساس کد استاد → کد درس → شماره گروه (برگه‌ها در روز امتحان مرتب) |
| ۲ — درهم‌سازی | Fisher-Yates Shuffle داخل هر بلوک (دوستان هم‌درس کنار هم نمی‌نشینند) |
| ۳ — استراتژی فیزیکی | **عادی** (پشت‌سرهم) / **زوج‌فرد** (بلوک اول صندلی فرد) / **یک‌درمیان** (زیگزاگ کامل بین بلوک‌ها) |

- **سالن‌ها:** `exam_halls` با هندسه (ردیف/ستون/ساختمان) — سالن آمفی‌تئاتر ۱۲۰ و سالن ۱ ۶۰
- **کارت ورود به جلسه = سه گلوگاه:** ① تراز مالی صفر ② ارزشیابی کامل اساتید ③ صندلی تخصیص‌یافته — سپس کارت چاپی با سالن/ساختمان/صندلی/بارکد اصالت‌سنجی
- **غیبت سیستمی:** ثبت غیبت → پیامک قالب `EXAM_ABSENCE` با مهلت ۴۸ ساعته (تاریخ شمسی) → درخواست «غیبت موجه» در کارتابل کارشناس → تایید: **حذف درس** / رد یا انقضای مهلت: **اعمال `unexcused_absence_policy` آیین‌نامه** (نمره صفر قطعی) + بستن خودکار ترم
- **مراقبین:** سرپرست/مراقب per سالن؛ لیست حضور و غیاب عکس‌دار قابل چاپ (نقشه رنگی صندلی‌ها + انتخاب غایب با کلیک)

دمو: کارشناس آموزش `0055555555` ← «مدیریت امتحانات» ← انتخاب استراتژی ← تولید صندلی‌ها ← نقشه سالن و حضور/غیاب. دانشجو ← «کارت ورود به جلسه».

## ماژول ۱۰-الف — حضور و غیاب طول ترم + قرارداد الکترونیکی ✅ (پیاده‌سازی شد)

وفادار به سند §۱۸۰۶–۲۰۴۰ در `src/engines/attendance.js`:

| قابلیت | توضیح |

| **گام ۴ — صدور شماره دانشجویی (§۲۴۳۴)** | سه گلوگاه سخت (همهٔ مدارک اجباری VERIFIED + KYC معتبر + پرداخت) ← یک کلیک ← شماره از **موتور فرمول‌ساز** `{Year:2}{Degree}{Major:3}{Seq:3}` + تبدیل پرونده به ACTIVE + نقش STUDENT + انتقال پرداخت به دفتر کل + پیامک شماره |
| **زونکن دیجیتال (§۲۴۴۵)** | ۴ پوشهٔ هویتی/تحصیلی/اداری-مالی/انضباطی-پزشکی — `document_types` داده‌محور (اجباری؟ نیاز به تایید؟) + اسناد الکترونیک امضاشدهٔ استاد در پوشهٔ اداری/مالی |
| **RBAC پوشه‌ای (§۲۴۸۳)** | `document_categories.accessRoles` — کارشناس مالی فقط «اداری/مالی» را می‌بیند (زنده تست شد)؛ دسترسی فایل از طریق `/api/files/:id` با گیت پوشه‌ای |
| **واترمارک دیجیتال (§۲۴۷۸)** | هر مشاهده/دانلود = واترمارک «کارشناس \| تاریخ \| IP» (هدر X-Watermark + Overlay قرمز در نمایشگر) + رکورد ARCHIVE_DOC_VIEWED در Audit — در صورت نشت فایل، دانلودکننده مشخص است |

API: متقاضی `GET /api/onboarding/me`، `POST /api/onboarding/{submit,upload,pay,kyc}` — کارشناس `/api/admin/archive/{import,inbox,doc-review,kyc-review,approve,dossier}` — فایل `GET /api/files/:id` (گیت: کارشناس بایگانی `0099999999` / مدیر).

دمو (متقاضیان با **رمز = کد ملی**): یاسر `1212123451` (آمادهٔ صدور — کارشناس یک کلیک → شماره دانشجویی) | مهدی `1212123452` (KYC ۷۸.۲٪ → بررسی چشمی + تایید مدارک) | سعید `1212123453` (KYC رد ۵۸٪ → پرداخت + تلاش مجدد). کارشناس بایگانی `0099999999` ← «🗄 بایگانی الکترونیک» (KYC چشمی، مدارک با واترمارک، صدور شماره، زونکن با جستجوی کدملی).

تست زندهٔ E2E ✓: تزریق سنجش + ورود رمز=کدملی — KYC بدون پرداخت ⛔ — پرداخت ۸٬۰۰۰٬۰۰۰ → KYC ۹۴.۱۵٪ AUTO_APPROVED — واترمارک فایل (X-Watermark + Audit) — مالی → پوشهٔ هویتی ⛔ — بررسی چشمی مهدی ✓ — صدور شماره ۵BS۴۱۲۰۰۷ از فرمول‌ساز → نقش STUDENT + my-grades ✓ — گلوگاه مدارک سعید ⛔ «۰ از ۴» — زونکن مالی=[اداری/مالی] vs بایگانی=[۴ پوشه].
