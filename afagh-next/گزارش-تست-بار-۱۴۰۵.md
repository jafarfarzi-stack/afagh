## ۱. سناریو و حجم داده

دادهٔ مصنوعی ولی ازنظر شکلی واقعی (همهٔ جداول موردنیاز موتور حقوق + مسیر نمرات) با seed قطعی ساخته شد
(`scripts/load-test-seed.mjs`، PRNG با seed=1405 — تکرارپذیر):

| موجودیت | تعداد |
|---|---|
| استاد (هیئت علمی + مدعو) | ۱٬۵۰۰ |
| دانشجو | ۳٬۰۰۰ |
| درس | ۳۰۰ |
| ارائهٔ درس (کلاس) | ۳٬۰۰۰ + ۳۰۰ کلاس هم‌یار (CO_LECTURER سهم ۵۰٪) |
| ثبت‌نام | ۳۳٬۰۰۰ (هر دانشجو ۵ درس + ۳۰۰ کلاس پرجمعیت ۶۰ نفری) |
| جلسهٔ کلاس | ۵۳٬۷۸۸ (۱۶ جلسهٔ اصلی + ~۳۰٪ جبرانی) |
| قرارداد ترمی | ۱٬۵۰۰ (FULL_TIME_FACULTY یا ADJUNCT) |
| سند الکترونیک | ۳٬۰۰۰ (قرارداد + ابلاغیه) |
| ترم | `LOAD-1405` (isCurrent=1) |

**توزیع گلوگاه (عمدی):** استادهای `i%3==0` → همهٔ نمرات `FINALIZED` و هر دو سند `SIGNED` (۵۰۰ استاد = گلوگاه باز)؛
بقیه مخلوط `TEMPORARY/DRAFT` + یک سند `PENDING` (۱٬۰۰۰ استاد = گلوگاه بسته).

Seed: **۵۱٫۷ ثانیه** (idempotent با نشانگر `LOAD_TEST_SEEDED`؛ پاک‌سازی دقیق با `--reset` بر اساس پیوند، بدون آسیب به کاربران دمو)

## ۲. اثبات عدم N+1

`loadTermPayrollData(termId)` برای کل ترم (۱٬۵۰۰ استاد، ۳٬۳۰۰ کلاس، ۵۳٬۷۸۸ جلسه):

```
🔍 loadTermPayrollData #1 → 11 کوئری
🔍 loadTermPayrollData #2 → 11 کوئری — ✅ ثابت (مستقل از تعداد استاد = عدم N+1)
```

توزیع دقیق (هر بار):

| # | کوئری |
|---|---|
| ۱ | ترم (`academic_terms`) |
| ۲ | ضرایب (`teaching_coefficients`) |
| ۳ | قواعد (`payroll_calculation_rules`) |
| ۴ | نرخ پایه (`teaching_rates`) |
| ۵ | قراردادهای ترم |
| ۶ | استادان ⨝ کاربران |
| ۷ | کلاس‌ها + هم‌کاران (یک SQL با LEFT JOIN) |
| ۸ | آمار جلسات (GROUP BY — همهٔ کلاس‌ها) |
| ۹ | گلوگاه ۱: نمرات قطعی‌نشده (GROUP BY — همهٔ استادان) |
| ۱۰ | گلوگاه ۲: اسناد امضانشده (GROUP BY — همهٔ استادان) |
| ۱۱ | فیش‌های حساب‌شده ⨝ قرارداد |

۲، ۳، ۴ (پیکربندی کوچک) بعد از اولین فراخوانی کش می‌شوند؛ ۷ کوئری حجمی دادهٔ ترم همیشه ثابت است.
**نتیجه: تعداد کوئری با تعداد استاد رشد نمی‌کند** — در نسخهٔ قبل (SQLite) به ازای هر استاد چند کوئری جدا می‌رفت.

## ۳. اجرای سنگین — نتایج

| عملیات | زمان | نکته |
|---|---|---|
| `computeTermPayroll` (محاسبهٔ فیش همهٔ ۱٬۵۰۰ استاد) | **۰٫۸۵ ثانیه** | **۱٬۷۷۴ فیش/ثانیه** |
| `getOverview` (داشبورد ۱٬۵۰۰ ردیف) | ۰٫۶۴ ثانیه | |
| علی‌الحساب میان‌ترم | **۲٫۱۶ ثانیه** (۵۰۰ استاد، ~۴ms/استاد) | مبلغ ۲٬۶۹۰٬۱۱۳٬۵۶۰ ریال (۴۰٪) |
| تسویهٔ نهایی **قبل از بهینه‌سازی** | **۳۲۰٫۴۲ ثانیه** | ~۶۴۱ms/استاد — ⚠️ گلوگاه |
| تسویهٔ نهایی **بعد از بهینه‌سازی** | **۶٫۵۸ ثانیه** | ~۱۳ms/استاد — **۴۹× سریع‌تر** |

**گلوگاه‌ها:** باز (واجد تسویه) ۵۰۰ · بسته ۱٬۰۰۰ — مطابق طراحی ✅

**تطابق مالی نهایی:** بودجه ۲۰٬۱۸۶٬۴۶۹٬۰۵۰ ریال = پرداخت‌شده ۶٬۷۲۵٬۲۸۳٬۹۰۰ + باقی‌مانده ۱۳٬۴۶۱٬۱۸۵٬۱۵۰ ✅

**راستی‌آزمایی گلوگاه:** تسویهٔ استاد مسدود → `گلوگاه تسویه: 11 نمره هنوز FINALIZED نشده است.` ✅

## ۴. گلوگاه یافت‌شده و بهینه‌سازی انجام‌شده (`src/lib/payroll-engine.ts`)

- **مشکل:** `settleFinal` برای هر استاد، *داخل تراکنش* `loadTermPayrollData(term.id)` را صدا می‌زد
  (برای اینکه چک گلوگاه با قفل سطری TOCTOU-safe بماند) → ۵۰۰ × ۱۱ کوئری سنگین ≈ ۳۲۰ ثانیه.
  این عملاً N+1 در مقیاس پرداخت بود.
- **راه‌حل:** تابع `loadStaffGates(tx, termId, staffId)` — همان منطق دقیق کوئری‌های گلوگاه، ولی فیلترشده
  برای یک استاد با **دو کوئری سبک** (مناسب ایندکس: `termId + professorId` و `termId + staffId`).
  چک همچنان *داخل همان تراکنش* انجام می‌شود؛ هیچ‌چیز از تضمین‌های همزمانی کم نشد.
- **نتیجه:** ۳۲۰٫۴۲s → ۶٫۵۸s (۴۹×) و کوئری/استاد در تسویه: ۲۳٫۱ → ۱۴.

## ۵. نحوهٔ اجرا

```bash
# ساخت داده (بار اول) یا بازسازی کامل با --reset
DATABASE_URL=postgres://afagh:afagh@127.0.0.1:5432/afagh_db node scripts/load-test-seed.mjs [--reset]

# اجرای کامل تست سنگین (warmup, load, compute, overview, midterm, settle, report)
DATABASE_URL=postgres://afagh:afagh@127.0.0.1:5432/afagh_db npx tsx --conditions=react-server scripts/load-test-run.mts
# اجرای فاز خاص: PHASE=load,compute … (مثلا PHASE=settle,report)
```

- `scripts/load-test-seed.mjs` — seed idempotent با `--reset` (پاک‌سازی بر اساس پیوند، امن برای کاربران دمو)
- `scripts/load-test-run.mts` — شمارندهٔ دقیق کوئری (patch روی `Client.prototype`)، زمان‌سنج فاز‌به‌فاز، گزارش تطابق
- نکته: import موتور در tsx نیاز به `--conditions=react-server` دارد (بابت `server-only`)
